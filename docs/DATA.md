# Данные и журналы

[На главную](../README.md) · [Запуск](GETTING_STARTED.md)

Все пути ниже указаны относительно [`Analitics/1/Arcanomics/`](../Analitics/1/Arcanomics/).

## JSON-справочники

| Файл | Формат | Использование |
| --- | --- | --- |
| `data/cities.json` | Объект `region_key → массив городов` | Вход для `graph.py` |
| `data/goods.json` | Объект `product_name → состояние товара` | Шаблон товаров, копируемый каждому городу |
| `data/roads.json` | Массив объектов `{u, v, routes}` | Выход генератора графа; при генерации перезаписывается |

Город задаётся полями `name`, `lat`, `lon`, `population`; необязательное `display_region` задаёт подпись региона. Имя становится идентификатором узла. Генератор дополняет запись региональным ключом и признаком центра. В Pyvis население передаётся как `population_base`.

Товар содержит `stock`, `base_price`, `last_price`, `current_price`. Текущие ключи — ровно `Commodity A`, `Commodity B`, `Commodity C`: они явно используются в JavaScript, поэтому добавление произвольного товара в JSON не означает полноценной поддержки всей системой.

Каждый элемент `routes` содержит `name`, `dist` в километрах и `speed` в км/ч. Генератор создаёт один вариант на дорогу. В массиве для браузера добавляется `id`, которого нет в сохраняемом JSON. Ручное изменение `roads.json` не меняет алгоритм построения сети.

## История погоды

Генератор ищет `data/weather_history/region_a.csv`, `region_b.csv`, `region_c.csv`, `region_d.csv`. Фактически в репозитории лежат `tokyo.csv`, `texas.csv`, `bavaria.csv`, `rostov.csv`; автоматического сопоставления нет. Поэтому при штатной генерации используются синтетические погодные ряды.

Парсер ищет строку заголовка, содержащую `time` и `temp` либо `rain`, затем читает значения по колонкам с подстроками `temp`/`temperature`, `rain`, `snow`, `wind_speed`/`wind`. Разделитель входного погодного файла — запятая. Значения по умолчанию при отсутствии колонок: 15 °C, 0 осадков, 0 снега, 10 км/ч ветра. Строки с некорректными числами пропускаются.

Дата `time` используется для обнаружения заголовка, но не для календарного выравнивания: в браузере записи выбираются по порядковому индексу часа с циклическим повторением. Произвольные CSV с запятыми внутри кавычек этим простым разбором не поддерживаются.

Имена существующих погодных файлов не гарантируют географию наблюдения: например, в метаданных `bavaria.csv` указаны координаты `45.79965, 12.2274885` и часовой пояс `Europe/Rome`. Перед сопоставлением файлов регионам нужно проверить метаданные.

## CSV-выгрузки симуляции

[`downloadSimulationResults()`](../Analitics/1/Arcanomics/src/simulation.js) предусматривает пять файлов. Разделитель — `;`, кодировка — UTF-8 с BOM. Значения заключаются в кавычки, внутренние кавычки удваиваются. Конечные нецелые числа округляются до двух десятичных знаков; в числах используется точка.

| Файл | Одна строка | Поля |
| --- | --- | --- |
| `simulation_log.csv` | Суточная сводка в 23:00 | `run_id`, `model`, `scenario`, `day`, `active_event`, `days_remaining`, `cooldown_remaining`, `production_multiplier`, `transport_multiplier`, `transport_cost_multiplier`, `price_multiplier` |
| `price_history.csv` | Средние по городам цены в 23:00 | `run_id`, `day`, `bread`, `wood`, `stone`, `event` |
| `weather_events.csv` | Запись из `EventSystem.eventHistory` | `start_day`, `end_day`, `duration`, `event`, `affected_resource`, `production_multiplier`, `transport_multiplier`, `transport_cost_multiplier`, `price_multiplier` |
| `routes_history.csv` | Запись из `roadHourLogs` | `run_id`, `road`, `trip_count`, `trip_profit`, `total_profit` |
| `city_economy_log.csv` | Город × товар × игровой час, до логистики | `run_id`, `model`, `scenario`, `seed`, `day`, `hour`, `city`, `product`, `stock`, `production_per_hour`, `demand_per_hour`, `fulfilled_demand`, `unmet_demand`, `current_price`, `weather_event` |

Исторические имена ценовых колонок сохранены:

| Колонка CSV | Товар в текущей модели |
| --- | --- |
| `bread` | `Commodity A` |
| `wood` | `Commodity B` |
| `stone` | `Commodity C` |

`stock` — количество товара после местного производства и продажи, до межгородской логистики. Поля `production_per_hour`, `demand_per_hour`, `fulfilled_demand`, `unmet_demand` измеряются в единицах товара за игровой час. Цены и прибыли — денежные единицы модели; некоторые подписи интерфейса называют их рублями.

Схема `routes_history.csv` не содержит времени, товара и отдельных колонок отправителя/получателя. `analytics.py` трактует `trip_count` и `total_profit` последней записи дороги как накопленные показатели. Текущий код не содержит функции, которая их наполняет; по схеме нельзя восстановить отсутствующий алгоритм перевозок.

`EventSystem.eventHistory` сбрасывается, но в текущем пути расчёта не пополняется. Поэтому пустой `weather_events.csv` не доказывает отсутствие локальной непогоды.

## Что считает аналитика

[`src/analytics.py`](../Analitics/1/Arcanomics/src/analytics.py) выводит:

- Волатильность каждого товара: выборочное стандартное отклонение суточных цен, делённое на среднее, в процентах.
- Долю дней с `bread > 40`. Несмотря на текст вывода о пустом складе, это ценовой порог, а не фактический stockout rate.
- Восстановление цены A после события до коридора менее 15% отклонения от медианы ряда; экстремальность определяется текстом поля `event`.
- Сумму последних `trip_count` по дорогам, среднее последних `total_profit` и три наиболее прибыльные дороги.

`simulation_log.csv` обязателен для запуска и читается, но его таблица далее не участвует в формулах. Скрипт не проверяет совпадение `run_id`, не разделяет несколько экспериментов в одном файле и не использует `city_economy_log.csv`. Поэтому сравнивать независимые прогоны следует раздельно, сохраняя комплект файлов каждого запуска.
